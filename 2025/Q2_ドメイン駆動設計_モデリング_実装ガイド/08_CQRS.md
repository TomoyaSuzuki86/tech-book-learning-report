# 08_CQRS

## 要点

* **CQRS (Command Query Responsibility Segregation: コマンドクエリ責務分離)** とは、「参照に使用するモデルと更新に使用するモデルを分離する」アーキテクチャである。
* DDDの戦術的設計パターンを使っていると、更新系処理は保守性が高いが、参照系処理（特に一覧画面などで複数の集約情報を表示する場合）で問題が発生することがある。
* 参照系処理で発生する問題として、複数の集約から値を取得して詰め替えるコードが読みにくい、パフォーマンスが悪化する、複数集約の条件で絞り込んでのページングができない、といった点が挙げられる。
* CQRSを導入することで、更新系モデル（ドメインオブジェクト）と参照系モデル（特定のユースケースに特化した値の型、例：DTO）を分離し、これらの問題を解決する。
* 参照用モデルの型はユースケース層に、それを取得するためのクエリサービスの実装クラスはインフラ層に配置する。
* クエリサービスの実装では、パフォーマンス最適化のために複数テーブルのJOINや必要なカラムのみのSELECTなど、自由にクエリを記述できる。
* CQRSのメリットは、コードのシンプル化、クエリパフォーマンスの向上、複雑な条件でのページング対応などである。
* CQRSのデメリットは、ドメインオブジェクトの参照場所が追いにくくなること、アーキテクチャが複雑になることである。
* CQRSは、システム全体に適用する必要はなく、**必要なところだけ部分的に導入することが可能**である。
* 参照用モデルの型をユースケース層に定義する理由は、最適な参照用モデルが個別のユースケースに依存するからである。
* 「CQRS = データソース分離」や「CQRS = イベントソーシング」は誤解であり、これらはCQRSと相性が良い別の概念である。

## 複雑な参照系処理を解決するCQRS

この章では、DDDでアプリケーションを構築する際に避けて通れない、**複雑な参照系処理の問題**とその解決策である**CQRS（コマンドクエリ責務分離）**について解説している。更新系処理はドメインオブジェクトとリポジトリで堅牢に構築できるものの、複数の集約にまたがるような一覧表示画面などでパフォーマンスやコードの複雑性が課題となる、という指摘は多くのエンジニアが共感できるだろう。

CQRSの核となるのは、「**参照用のモデルと更新用のモデルを分離する**」という思想だ。更新系では、これまで学んだドメインオブジェクト（エンティティ、値オブジェクトなど）を使い、厳格な整合性を保つ。一方で参照系では、特定のユースケース（例えば、一覧画面）に特化した専用のデータ構造（DTOなど）を定義し、それを効率的に取得するための「クエリサービス」を設ける。これにより、参照処理ではドメインオブジェクトの厳密な制約を気にせず、パフォーマンスを最大化するような自由なクエリ（例：複数のテーブルをJOINしたり、必要なカラムだけ取得したり）を書けるようになる点は非常に魅力的だ。

クエリサービスは、インターフェースをユースケース層に、実装をインフラ層に置くことで、ユースケース層は「どんなデータが欲しいか」という抽象的な要求だけを持ち、具体的な取得方法（DBアクセス方法やORマッパーなど）は隠蔽される。最適な参照用モデルは個々のユースケースに依存するため、参照用モデルの型がユースケース層に定義されるという説明は、この責務分離の意図を明確にしている。

CQRSの導入には、コードのシンプル化やパフォーマンス向上といった明確なメリットがある一方で、アーキテクチャが複雑になる、ドメインオブジェクトの参照箇所が追いにくくなる、といったデメリットも存在することを本書は指摘している。このため、常にCQRSを導入すれば良いわけではなく、**問題の大きさやメリット・デメリットを考慮して部分的に導入する**という pragmatic な（実用的な）判断が重要であると強調している。

また、「CQRS = データソース分離」や「CQRS = イベントソーシング」ではない、という誤解の解消も重要だ。これらはCQRSと相性が良い別の概念であり、それぞれが異なる問題（パフォーマンス、証跡記録など）を解決するためのものであることを理解する必要がある。CQRSは、DDDにおける複雑な参照系処理という、多くが直面する課題に対する強力な解決手段であり、その適切な導入はアプリケーションの持続可能性に大きく貢献すると感じる。
